# 短训轨迹与数据协议审计

审计时间 2026-11-26。代码 HEAD `a88566e`。实验根目录 `/root/data/experiments/TTSR-lowlight-block-amend`。只读现有产物，没有训练，没有改 checkpoint、清单或评测 JSON。`short_ft_r3` 不在本次范围内。没有做无梯度分解推理：逐图 JSON 已经回答 Real ep4 是普遍下降还是少数图主导。

## 直接回答

1. **没有确认的代码、产物配对或缓存错误。** 三个数据集各 5×3 个短训权重都能按 schema 4、`csfi_lfca_v1` 加载。每一段里 5 个 epoch 的 `model_state_dict` 指纹互不相同。官方测试 JSON 里的 `checkpoint_path` 和 `checkpoint_epoch` 对得上现在磁盘上的那个文件。逐图 PSNR/SSIM 的算术平均等于 JSON 里的汇总值。样本数是 Real 64/100、华为 50/30、尼康 50/20。JSON 里没有生成当时的 checkpoint 哈希，所以「文件自写出以后没被换过」只能核对到当前路径，不能补写成历史保证。

2. **同一 local epoch 的训练顺序和几何增强，按开训前就冻结的代码会重播。** 这不是从 11 月 20 日的运行日志里捞出来的逐步轨迹。它也不证明重播造成了 ep4 的下跌。

3. **Real 官方 Test 的 ep4 下跌发生在大多数图上。** 中位数比均值更低，最差的 10 张只解释均值跌幅的大约三分之一。内部验证是大约一半图下降，另外有一组三轮都重复出现的重跌样本。

4. **没有 light-up / residual 的分解证据。** ep4 的 `frac_gt1` 大约从 0.001 升到 0.004–0.006，和变亮相关，但越界像素仍不到 1%，不能把它当成 1.2 dB 的解释。

5. **尼康的分歧不是参考链接、缺对或指标协议造成的。** 有参考的 500 张是「Train 里凡是有参考的都收进来」，不是从更大的有参考集合里抽样。测试集 Low 更亮、参考相对 GT 更暗，但分布和训练/验证重叠。验证集整体变差、测试集多数变好，是两组图各自的方向，不是同一张图被算了两次。

6. **没有确认需要改的 bug。** 下一步如果还要追 ep4 的机制，只对已经固定的内部验证子集做无梯度整图分解。不要再开短训，也不要按官方 Test 另选起点。

## 产物对应

第 1 轮的 `init_checkpoint` 是本数据集的 `checkpoint_best_val_psnr.pt`。Real 的父 epoch 是 100，华为是 92，尼康是 79。第 2 轮的父文件是第 1 轮的 `checkpoint_epoch_0005.pt`。9:1 一轮的父文件是第 2 轮的 epoch 5。没有跨数据集路径。

`load_strict_state` 只加载模型权重。短训新建 Adam。Real 第 2 轮的 Adam `step` 是 143、286、429、572、715，`global_step` 相同，`scheduler.last_epoch` 是 1 到 5。这不是把 100 epoch 的优化器接着数。pack 里的学习率是 `1e-5`，`gamma` 是 1。日志里的 `Epoch k lr=1e-05` 与此一致。`rec_w/ms_ssim_w` 在前两轮是 1/1，在 `short_ft_w91` 是 9/1。

队列脚本在评测目录已存在时直接退出，它不检查 JSON 是否完整。本次抽查的 JSON 本身是完整的：ID 唯一，五个 epoch 的 ID 集一致，数值有限，协议是 `rgb_float_clipped_v1`，没有改成 PNG 量化或 GT 均值对齐。

## 数据顺序和增强

`dataset/block_amend_lolv2.py` 自 `92b9014`（2026-11-19 23:05，这些 run 开始之前）到 HEAD 没有 diff。增强种子是 `SHA256(f"{seed}|{epoch}|{sample_id}")` 的前 16 个十六进制位，不用 Python `hash()`。`train_loop` 用它打印的那个 epoch 整数调用 `set_epoch`。每段短训日志都从 Epoch 1 开始。

Shuffle 用 `prepare_data` 里新建的 `torch.Generator`，`manual_seed(config.seed)`。三个数据集的 pack 都是 seed 42、crop 160、batch 4、`num_workers` 4。`drop_last` 后 Real 每 epoch 143 个 batch，与 Adam step 相符。验证 loader 是 `shuffle=False`，不消耗这个 generator。几何增强用自己的 `random.Random(stable_aug_seed(...))`，不看 worker 的全局随机数，也不看模型初始化消耗了多少全局随机数。

因此，在图像高宽不变的前提下，三段短训的同一个 local epoch 具有相同的样本顺序、相同的 crop / rot90 / flip，以及相同的末尾 batch。高宽是现在从文件头读的，11 月 20 日没有存档。重放结果写在 `augmentation_replay_summary.json` 和 `augmentation_trace.jsonl`。

末尾 10 个 batch 的亮度用固定定义 `0.299R+0.587G+0.114B`，再除以 255。Real 的 Low 均值在 epoch 3/4/5 是 0.062 / 0.057 / 0.062。epoch 4 的尾批并不更暗。这只否定「尾批曝光特殊」这一个表面解释，不证明别的原因。

**重播相同序列是代码结论。它没有被证明为 ep4 下跌的原因。** 三段的起点权重不同，模型指纹也不同，但 ep4 仍下跌。共享的数据序列是一个共同条件，不是干预实验。

## Real 的 ep4

官方 Test，ep3 → ep4，n=100：

| 阶段 | 均值 | 中位数 | 下降张数 | 下降超过 1 dB | 最差 10 张对均值的贡献 |
|---|---:|---:|---:|---:|---:|
| short_ft_5ep | -1.240 | -1.574 | 79 | 69 | -0.397 |
| short_ft_r2 | -1.231 | -1.566 | 78 | 69 | -0.412 |
| short_ft_w91 | -1.542 | -1.889 | 81 | 71 | -0.464 |

中位数低于均值，是因为大约 20 张图在变好，把均值往上拉。典型图的跌幅大于平均值。最差 10 张大约只占 1.2 dB 均值的三分之一。三轮共同出现在最差 10 张里的测试 ID 是 00712、00713、00716、00731、00737、00738、00773、00774。

内部验证，n=64：均值 -0.243 / -0.358 / -0.415，中位数 -0.165 / -0.355 / -0.316，下降 33、34、33 张，其中超过 1 dB 的有 24、26、28 张。最差 10 张对均值的贡献是 -0.624 / -0.656 / -0.698，大于均值本身，说明验证集均值里有一个重尾，其余图有升有降。三轮都进入最差 10 的验证 ID 有 9 个，包括 00053、00595、00215、00009、00579、00603、00638、00651、00308。

验证集和测试集的 ID 不重叠。两边都在 ep4 变差，测试集更整齐，验证集更依赖重尾。不是同一批图被重复计数，也不是评测缓存把某一轮的 JSON 套到了另一轮：checkpoint 路径和模型指纹都按 epoch 分开。

`frac_gt1` 的均值大约从 0.001 升到 0.004–0.006，ep5 又降回去。这和原始输出有更多像素超过 1 同步，但面积太小，不能单独解释多数图超过 1 dB 的 PSNR 变化。`examples_real_r2_test/` 里是第 2 轮测试图 00712、00773、00774 在 ep3/ep4/ep5 的已裁剪 PNG 符号链接，只能看外观，不能重算 float 指标，也不能读出 `log_gain` 或残差。

没有跑第 5 节的 15 次诊断前向。缺的是整图、按真实 tile 羽化拼回去的 base 与 residual，以及 `raw ≈ base + residual` 的核对。

## 尼康

现场清点：`collect_triplets` 在 Train 上得到有参考 500、缺参考 2650。manifest 的 450+50 正好等于这 500，不是另外抽的子集。官方 Test 20 张，缺参考 0。20 个测试参考都是 `.jpg` 名字的符号链接，目标是 `Eval/Nikon/nanobanana_ref_Nikon/*.png`。

ID 字符串 3004、3016 同时出现在 train 和 test，3017 同时出现在 val 和 test。Low 文件哈希不同，路径分别在 `Train/Low` 和 `Test/Low`。跨 split 的相同 realpath 数量是 0。相同 ID 字符串排除不了「同名不同场景」，这次哈希说明它们不是同一份 Low 文件。

有一对内容重复：train `149` 和 val `337` 的 Low 字节相同（`ce9c2f0cceff…`），路径不同。只核了 Low，没有核 GT 和参考。一对图解释不了 3.7 dB 的验证/测试差。

亮度用同一套 `0.299R+0.587G+0.114B` / 255，事先定死，没有按测试分数调阈值。

| 集合 | n | Low 中位数（最小–最大） | GT 中位数 | Ref 中位数 | log2(GT/Low) 中位数 | log2(Ref/GT) 中位数 |
|---|---:|---|---:|---:|---:|---:|
| train | 450 | 0.090（0.005–0.352） | 0.402 | 0.316 | 2.014 | -0.382 |
| internal val | 50 | 0.089（与 train 同量级） | 0.395 | 0.312 | 2.078 | -0.342 |
| official test | 20 | 0.168（0.033–0.379） | 0.487 | 0.277 | 1.519 | -0.798 |

测试 Low 的中心比有参考训练集更亮，测试参考相对 GT 更暗。训练 Low 的最大值 0.352 已经盖住测试的大部分，测试最小值 0.033 也落在训练范围内。n=20，这里只报告分位数，不把它写成显著性检验或「真实噪声水平」。

100 epoch 内部最佳对上 `short_ft_r2` epoch 5，按 ID 配对：

- 内部验证 50 张：均值 -0.299 dB，中位数 -0.271，29 张下降、21 张上升。最差 5 张贡献 -0.252，接近整个均值，所以重尾很大，但下降方向仍是多数图。
- 官方 Test 20 张：均值 +0.243 dB，中位数 +0.166，15 张上升、5 张下降。最差 5 张的贡献是 -0.094，没有把均值拉成负数。

两边方向相反，而且重叠 ID 并不是同一文件。这不支持「协议用错了所以符号相反」。它支持的是：这 50 张验证图和这 20 张测试图对同一次短训的响应不一样。覆盖子集是全部有参考的 Train，不是按亮度挑选的；测试集不在这个 500 里。
